## Problem Statement

Five friends have spent months in a WhatsApp group without confirming a trip. A Google Form got 3 of 5 responses and a WhatsApp poll collapsed when two people changed their minds. The app turns everyone's constraints into 2-3 ranked options (destination + date window) and shows where each person stands on each one, so the group makes one decision.

## What Makes This Cool

The tool asks the questions, so the organiser stops being blamed. And every ranking can be explained: each option shows each friend's score and a plain reason. There's no AI and no black box.

## Constraints (fixed by the brief, not up for debate)

- **Scope:** exactly the brief's 6 numbered v1 items. In the PRD these are v1 scope items 1-7 plus FR13 (mark final). Nothing from the PRD's "Out of scope (Phase 2)" list.
- **Stack:** Next.js, Supabase (Postgres), Vercel.

- **Devices:** every page must work on a phone, because friends open it from WhatsApp (FR12).

### Worked example behind D1 (use it as a test case)

Both options cost ₹10,000 and are fully in season. Scores are rounded to whole numbers, as in rule 2.

| Friend | Wants | Budget | Goa (beach) | Manali (hills) |
|---|---|---|---|---|
| Asha | beach | ₹20,000 | 100 | 70 |
| Bilal | beach | ₹18,000 | 100 | 70 |
| Chirag | hills | ₹12,000 | 48 | 78 |
| Dev | beach | ₹25,000 | 100 | 70 |
| Esha | no preference | ₹15,000 | 85 | 85 |
| **Lowest / Average** | | | **48 / 86.6** | **70 / 74.6** |

- Old rule (worst-off first): **Manali wins**.
- New rule (floor 40, then average): **Goa wins**.
- Test case 2: raise Chirag to ₹15,000. Chirag scores Goa 70 and Manali 100, the averages become 91.0 and 79.0, and **Goa still wins**.
- Under the old rule, both lowest scores are now 70 (a tie). The old tie-break (group average) then picks Goa. So the old rule flips from Manali to Goa just because one person's budget changed. The new rule doesn't flip.

## Scoring rules (final, replaces the PRD's "Scoring logic" steps 1-5)

An **option** is one destination plus one candidate date window: 10 destinations × 3-4 windows = 30-40 options. Only people who have submitted count.

1. **Hard filters.** A person is *blocked* on an option if they didn't tick that window, or the destination has an attribute they ticked as a dealbreaker. Record who is blocked and why.
2. **Score each unblocked person, 0-100.** Score = 0.5 × budget + 0.3 × type + 0.2 × season, rounded to a whole number.
   - **Budget (0-100):** 100 if cost ≤ 70% of their ceiling. 0 and an **over budget** flag if cost > ceiling. A straight line in between.
   - **Type (0-100):** 100 if it matches, 50 for no preference, 0 if it doesn't match.
   - **Season (0-100):** the share of the window's days that fall in the destination's best months.

   The group average comes from these whole-number scores. For ranking it's compared exactly as a sum, and it's displayed to 1 decimal.
3. **Passing options.** An option *passes* if nobody is blocked, nobody is over budget, and every person scores **40 or more** (the floor).
4. **Rank the passing options** by group average (high first), then lowest individual score (high first), then cost (low first), then destination name A-Z. The last step guarantees the order never changes on refresh.
5. **Pick what to show.** Keep only the best-ranked window for each destination (R-2), then show the top 3 passing options.
   - If fewer than 2 pass, fill up to 2 with **flagged** options, ranked by rule 6.
   - The one-per-destination rule applies across both lists: a destination already shown as passing is skipped in the flagged fill, and each flagged destination appears once, in its best flagged window.
6. **Rank flagged options** (everything that didn't pass, including blocked ones):
   - first by the number of people with any problem (blocked, over budget, or under the floor), fewest first;
   - then by lowest score among unblocked people, highest first (0 if everyone is blocked);
   - then cost, then name.

   Label every problem in plain words, using these exact forms:
   - "Priya can't make these dates"
   - "Dev: trekking is a dealbreaker"
   - "Chirag: over budget"
   - "Esha: poor overall fit" (unblocked and within budget, but scores under 40)

   A person with several problems gets **one** label only: the first that applies, in the order dates → dealbreaker → over budget → poor overall fit. They count once in k.
7. **Partial responses.** Label the result "Based on 4 of 5. Waiting on: Karan." With fewer than 2 submitters, show the status page only and no ranking.
8. **Per-person reason.** Three exact phrases joined with " · ", in the order type · budget · season, with the first letter capitalised.
   - **Type:** "got beach" (a match), "wanted hills" (the person's own choice, when it doesn't match), "any type" (no preference).
   - **Budget:**
     - "comfortable on budget" when cost ≤ 0.7 × ceiling;
     - "tight on budget" when 0.7 × ceiling < cost ≤ ceiling;
     - "over budget" when cost > ceiling.

     No friend's budget amount ever appears. Destination cost per person *is* shown on the results page, because the group needs it to decide.
   - **Season:** "in season" when share ≥ 0.5, "partly in season" when 0 < share < 0.5, "off season" when share = 0.
   - Blocked people instead get their problem label from rule 6.
   - Example: "Wanted hills · tight on budget · in season".
9. **"Why it ranks here" line**, one per shown option.
   - **Passing options** (nobody over budget, by definition): "Everyone can afford it · {m} of {N} got their trip type · {season phrase}". Here m counts matches only, not "any type", and the season phrase uses rule 8's wording for the option's window. Example: "Everyone can afford it · 3 of 5 got their trip type · in season".
   - **Flagged options:** "Problem for {k} of {N}: {labels}", with one label per person from rule 6, in participant-list order, joined with "; ". Example: "Problem for 2 of 5: Priya can't make these dates; Chirag: over budget".

## Access design (D2 + D3 in plain English)

- **The browser never talks to Supabase.** Every page load and form save goes to Next.js server code. That code checks the visitor's cookie, then reads or writes the database with the secret Supabase key. The secret key lives only in Vercel's environment settings and never in any file the browser downloads.
- **Creating a trip gives the organiser three things:**
  - the **trip link**, with a long random ID, which goes in WhatsApp;
  - a **6-digit PIN**, which also goes in WhatsApp;
  - a private **organiser link**, which the organiser keeps to themselves. The screen says "Save this link. It's the only way to lock or finalise the trip", with a copy button.

  The PIN is shown only on this creation screen and on the organiser page, never on pages friends see.
- **Joining.** Open the trip link, enter the PIN, pick your name. The server then sets a signed, browser-hidden cookie, so that phone doesn't need the PIN or name again.
  - The cookie records which PIN version it was issued under. When the organiser regenerates the PIN, old cookies stop working.
- **Switching names.** Every page shows "You're Asha. Not you? Switch", which clears the name (not the PIN) and goes back to the name picker. This covers a first-time wrong tap and a phone shared between two friends.
  - Switch also gives the phone a **new device ID**. So on a shared phone, opening the other friend's name counts as "a different phone": the guard below fires and the budget stays hidden.
  - The save button reads "Save as Bilal", so a wrong name is visible before anything is saved.
  - Anything already saved under the wrong name still stays until its real owner overwrites it. The status page's "last updated" time shows it happened. *(Accepted risk: until then, those answers count in the results and in "N of 5".)*
- **Wrong-name guard.** Each phone gets a random device ID, saved with that person's answers.
  - If someone picks a name whose answers were saved under a *different* device ID, the app asks once: "Bilal's answers were saved in a different session. Is this really you?"
  - **Yes** switches the saved device ID to this one. The form then opens with everything pre-filled **except the budget, which must be typed again**, so a mis-tap never reveals a friend's number.
  - **No** goes back to the name picker and changes nothing: not the cookie and not the saved device ID.
  - If the original phone is used later, it asks once again, in the same way.
  - On a shared phone, the real owner is also asked (and retypes the budget) after any Switch. That's intended: it's the price of never showing one friend's budget to another.
- **PIN try limit.** Wrong PINs are counted per trip, and the count goes up in a single database update so two tries at once can't both slip through.
  - After 10 wrong tries, entry pauses for 15 minutes with the message "Too many wrong tries. Try again in N minutes."
  - The count resets on a correct PIN or when the pause ends.
  - One friend's mistyping can briefly pause everyone else too. That's accepted for five friends.
- **Deadline and lock.** Saving is allowed only while all three are true:
  - the server's time is on or before the deadline (for example 30 Sep 23:59:59 IST, so a save at 23:59:30 is accepted);
  - the organiser hasn't locked the trip early;
  - no final decision is set (R-3).

  The deadline is shown everywhere as, for example, "Fri 30 Sep, 11:59 PM IST".
- **Organiser-only actions** work only from the organiser link: lock early, regenerate the PIN, mark final and change or clear the final choice.
  - **Lock early / unlock.** Locking asks first: "Lock now? Friends can't edit until you unlock." It can be undone with Unlock any time before the deadline.
  - **Regenerate PIN.** This comes from the PRD's risk table ("The organiser can regenerate the PIN") and exists in case the PIN leaks outside the group. Friends whose cookie was issued under the old PIN see the PIN screen again with "The PIN has changed. Ask the organiser for the new one."
    - **It also issues a new organiser link** (review checkpoint 1, 2026-09-26). The old organiser link stops working, and the new one is shown once, with "Save this link". This way, regenerating recovers even if the organiser link leaked along with the PIN.
  - **Mark final.** Only options shown on the results page (passing or flagged) can be marked final. That's intended: the tool's job is to pick one of the 2-3 shown options.
    - The final choice can be changed or cleared. It never touches the early-lock setting (R-3). Clearing it brings editing back, unless the deadline has passed or the trip is locked early.
  - **How friends see the decision.** Once a final choice is set, a banner at the top of every trip page reads "Decided: Goa, 12-16 Dec". The ranking stays below it, headed "Results (locked)" (R-1), so it's never confused with the decision itself.
  - The organiser submits their own preferences the normal way, like everyone else.
- **Accepted risks** (a friend who has the PIN can do these; fine for five friends):
  - pick another friend's name and change their answers on purpose;
  - roughly work out someone's budget from their exact score, since fit scores must be shown (FR8) and costs are known;
  - the builder can see everything in the Supabase dashboard;
  - someone holding a leaked trip link could keep PIN entry paused by sending 10 wrong PINs every 15 minutes (the pause is per trip);
  - a save that starts a split second before the organiser locks or finalises can still land (a window of milliseconds).

## Data model (the PRD's 3 tables, fields filled in)

- **trips:** id (long random), name, participant_names (list), windows (list of {id, label, start date, end date}), deadline (date + time, IST), pin, pin_version, organiser_token, locked (yes/no), final_destination_id, final_window_id, failed_pin_tries, pin_paused_until, created_at.
  - The PIN is stored as-is so the organiser page can show it again for re-sharing. That's acceptable because the database never reaches the browser.
- **responses:** trip_id, participant_name, budget_inr, available_window_ids, dealbreakers, trip_type, device_id, updated_at.
  - Only one response is allowed per trip and name (FR2); a second save updates the same row.
- **destinations:** id, name, cost_per_person_inr, best_months, trip_type, attributes (the dealbreaker tags).
  - About 10 rows, costs and months checked by hand.
  - **Cost assumption:** the cost is the typical per-person spend on the trip itself (stay, food, local travel), *plus* return travel from one **reference city**. The reference city is fixed once, when the destination sheet is filled in; it isn't a per-trip setting.
  - The friends live in different cities, so this is an estimate. The form says it next to the budget field: "Costs assume travel from Pune." Dealbreaker tags must not depend on where someone starts. Use "international", "trekking" and "overnight journey from the reference city", not a vague "long flight".

## Reviewer Concerns

### R3-1 — consistency

**Problem**

> The document gives three different models of how 'final' and 'lock' interact. 'Deadline and lock' treats a set final decision as its own save-blocking condition, separate from the organiser's early lock. Open Question 1's default says 'marking final locks the trip, and clearing the final unlocks it'. 'Mark final' says clearing brings editing back 'unless the deadline has passed or the trip is locked'. If marking final sets locked = yes, then clearing can never bring editing back under the third rule. If clearing unlocks, it also silently undoes an early lock the organiser set before finalising. The engineer cannot tell which one to implement.

**Remedy**

> Pick one model and use it in all three places. For example: a set final is an independent save-blocking condition that never touches the locked field, and clearing it restores editing only if the trip was not locked early and the deadline has not passed. Reword Open Question 1's default to match, for example 'marking final stops edits; clearing it restores them'.

### R3-2 — clarity

**Problem**

> R-1 labels results 'Provisional' 'until the trip locks, then Results (locked)'. But editing can stop in three separate ways: deadline passed, early lock, or final set. Early lock can also now be undone with Unlock. The document does not define which of these states counts as 'locked' for the label. It also does not say whether the label goes back to 'Provisional' after Unlock or after the final is cleared. And if Open Question 1 is answered 'no', the 'Decided' banner sits above a ranking headed 'Results (locked)' while friends can still edit.

**Remedy**

> Define the label from the same condition that blocks saving: 'Results (locked)' exactly when saving is blocked (deadline passed, locked early, or final set under the chosen R3-1 model), otherwise 'Provisional: can change until [deadline]'. State that Unlock and clearing the final return it to 'Provisional' when editing resumes.

### R3-3 — completeness

**Problem**

> Rule 6 counts 'under the floor' as a problem, and rule 9's flagged line lists 'the problem labels from rule 6'. But rule 6 defines wording only for a missed window, a dealbreaker and over budget. There is no label for a person who is unblocked and within budget but scores under 40. The flagged line and the per-person reason therefore cannot be rendered deterministically for the most common flagged case the floor creates.

**Remedy**

> Add an exact under-floor label to rule 6, for example '{name}: poor fit (score 32)' or '{name}: below the floor', and include it in the scoring string tests.

### R3-4 — clarity

**Problem**

> Rule 9's flagged template 'Problem for {k} of {N}: {labels}' does not give the separator between labels. It also does not say what happens when one person has more than one problem: blocked on the window and on a dealbreaker, or over budget and also under the floor. That person is counted once in k but may produce several labels. Test 9 only covers the Goa/Manali example, where both options pass, so the flagged string is never tested word for word.

**Remedy**

> Specify the separator (for example ', '), and say whether a person with several problems gets every label or only the first one in a fixed priority order (window, dealbreaker, over budget, under floor). Add a flagged-option case to test 9.

### R3-5 — clarity

**Problem**

> Switch gives the phone a new device ID. So on a shared phone, when the real owner switches back to their own name, the guard fires with 'Bilal already submitted from another phone. Is this really you?', which is false because it is the same phone. The owner must also retype their budget every time the phone changes hands. The document does not state this consequence or adjust the wording.

**Remedy**

> State that after any Switch the real owner is also asked to confirm and must retype the budget, and that this is intended. Reword the guard neutrally, for example 'Bilal's answers were saved from a different session. Is this really you?'.

### R3-6 — completeness

**Problem**

> The wrong-name guard specifies what 'yes' does but not what 'no' does: whether it returns to the name picker, keeps the name in the cookie, or leaves the device ID unchanged.

**Remedy**

> Specify that 'no' returns to the name picker without changing the cookie name or the saved device ID.

### R3-7 — clarity

**Problem**

> D2 says 'no rupee amounts shown' and rule 8 says 'Rupee amounts never appear'. But the accepted risks say budgets can be inferred because 'costs are known', and rule 4/6 rank by cost. The document does not say whether each destination's per-person cost is displayed on the results page, or whether 'no rupee amounts' covers only friends' budgets.

**Remedy**

> State whether destination cost per person (from the reference city) is shown on the results and form pages. Narrow D2 and rule 8's wording to 'no one's budget amount is ever shown' if destination costs are displayed.
